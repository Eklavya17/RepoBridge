# Multi-Agent Reasoning for Large-Scale Repository 
Eklavya Tyagi (etyagi2), Sunwoo Baek (sunwoob2), Vishal Kaushik (vishalk2)

Large software repositories remain difficult for LLM-based quality-assurance systems because the evidence needed to diagnose or improve a program is often distributed across many files, modules, dependencies, and long execution paths. Existing repository-level agents such as RepoAudit show that demand-driven exploration can scale code auditing beyond a single file, but large-repository workflows still struggle with context selection, repeated exploration, and maintaining a consistent understanding of how different parts of the codebase interact [1]. These limitations affect more than debugging: performance bottlenecks may span several modules, while concurrency failures depend on interactions among threads, locks, shared state, and particular execution schedules. Our project therefore targets three repository-scale QA tasks--debugging and vulnerability detection, code optimization, and concurrency/race-condition repair--through a common multi-agent framework designed around better repository representation and context management.
The system will first ingest the repository and build a structured representation of what exists in the codebase and how execution moves through it. This representation will include files and modules, symbols, dependencies, call relationships, control/data-flow information, tests and build information, and synchronization state such as shared variables and locks; runtime traces and profiling information will be attached when the program is executed. These artifacts form a shared program state that acts as the memory of the multi-agent workflow. Rather than repeatedly parsing the repository or placing large amounts of raw code in every prompt, agents will query this state to locate specific elements, identify paths that reach them, extract relevant program slices, and determine how to execute those paths to reproduce an observed issue.
A coordinator will decompose each QA task and route work to specialized agents that communicate through NLIP [6]. MCP-backed tools will expose repository search, graph traversal, forward/backward slicing, build and test execution, profilers, sanitizers, and race-detection tools. For debugging, the system will connect failures or issue reports to relevant execution traces and slices before generating and validating a fix. For optimization, it will combine profiling data with call/data-flow context to identify cross-module bottlenecks and verify improvements through repeatable benchmarks. For concurrency, it will reason explicitly about threads, shared state, locks, and state transitions, then reproduce and validate candidate races or repairs using concurrency-aware tests. ProtocolGuard motivates our use of program slicing and concrete verification, but our approach applies these ideas to general repository QA rather than protocol specifications [3]. We will compare against repository-level and general software-engineering agent baselines such as RepoAudit, SWE-agent, and OpenHands [1,8,9], using SWE-bench and task-specific debugging, optimization, and concurrency workloads [7]. Evaluation will measure task success together with context/token usage, runtime, and the amount of repository exploration required.
RQ1 - Debugging & Vulnerability Detection: How can a multi-agent framework improve debugging and vulnerability detection when relevant evidence is distributed across long call chains, multiple files, and different parts of a large repository?
RQ2 - Code Optimization: Can multi-agent reasoning with shared repository context improve runtime, memory, and storage optimization when performance bottlenecks span multiple functions or modules?
RQ3 - Concurrency & Race Conditions: Can explicit multi-agent reasoning over threads, locks, shared state, and state transitions improve the detection and repair of race conditions in large real-world repositories?
